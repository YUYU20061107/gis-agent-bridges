# 工程文件生产手册（Global Mapper / .gmw 适配版，未实机验证）

本手册把 SuperMap 包 2026-10-24 实机校准沉淀的通用工程纪律，按 Global Mapper
的形态（无头为主 + 脚本半实时、无常驻应用内桥）改写。**本包尚未在真实
Global Mapper 上校准**：手册里涉及 `globalmapper` 模块函数名/签名的说法都是
待实机验证的假设，纪律部分（原件只读、写后重读等）是通用要求、立即生效。

## 1. 原件只读：先备份、只改副本

- 任何写操作之前，先用 `scripts/gm_bridge.py backup` 给 .gmw 生成带时间戳的
  备份副本（回报含 sha256）。真实要改的，永远是另行复制出的**工作副本**，
  不是原件、也不是备份本身。
- `inspect` 的模块路线先把工程复制到临时目录再打开、文本路线只读字节——
  盘点类动作天然不碰原件；不要为了省事改成直接打开原件。
- 验收时核对原件 mtime 全程未变（见第 7 节清单）。mtime 变了就是纪律破了，
  如实回报，不要掩盖。

## 2. 伴生文件完整性（.gmw 只是引用表）

- .gmw 保存的是图层引用关系，真实数据在外部文件里。只复制 .gmw 不等于
  搬走了工程：迁移时连同被引用文件一起处理（`verify_project.py --copy-to`
  会复制工程、同主名伴生与同目录被引用数据的伴生集）。
- Shapefile 是成套文件：`.shp/.shx/.dbf` 缺一不可，`.prj/.cpg` 缺失分别
  意味着坐标系与编码信息丢失。交付/迁移前用盘点输出逐项核对伴生集，
  缺必需件记为 issue，不要当作可忽略的小事。
- 其他格式同理成组看待：栅格的 `.hdr`、世界文件、`.xml` 元数据等，
  凡同主名成组出现的文件都按伴生集整体搬运与校验。

## 3. 相对路径风险

- 工作区里的数据引用常是相对路径：工程换目录后，相对引用会按新目录重新
  解释，数据“连不上”时盘点会误报图层为空——先怀疑路径，不要先怀疑数据丢了。
- 只复制工程文件到新目录再打开，相对路径数据源会断链（SuperMap 校准时
  同类问题实测复现：inspect 必须连带复制相对路径数据源）。迁移验收必须
  走 `verify_project.py --copy-to` 对副本重开盘点，而不是只看复制成功。
- 引用里出现盘符/绝对路径的，换机器必然断链，盘点回报里要单独点名。

## 4. 写后重读验证持久化（不信 API 返回，警惕假成功）

- 函数调用没抛错 ≠ 改动落盘。任何写动作之后，必须**重开工程副本重读**，
  以重读到的状态（图层数、图层名、显隐、导出图内容）为准回报。
- SuperMap 校准实测过“假成功”：旧专题路径只改了 Python 包装对象，
  既不渲染也不进工程 XML，改前改后导出图哈希相同。Global Mapper 的模块
  函数同样多为多策略试探——命中 `via` 只是“这个函数名调通了”，不是
  “效果对了”；以重读与导出图为最终证据。
- 导出类动作以“目标路径真有新文件落盘且字节数 > 0”为成功标准
  （`export_workspace_image` 已按此实现）；没文件就是失败，如实回报。

## 5. GUI 刷新 / 无头边界（半实时，如实写）

- 本包没有常驻应用内桥：无头进程 import `globalmapper` 模块看到的是
  模块自己的会话，不是 Global Mapper 桌面里正打开的那个工程。
- 只有从桌面 Script Editor 以“Run Script in the Context of the Main View”
  启动的脚本上下文，才可能碰到主视图已加载图层——这是**半实时**：
  无推送、界面何时刷新取决于 Global Mapper 本身，不许宣称实时接入。
- 无头上下文下视图类工具被上下文闸挡住（`NOT_IN_MAIN_VIEW_CONTEXT`）
  是设计行为。严禁用伪造环境变量声明 main-view 上下文绕闸。
- GUI 里未保存的改动，磁盘盘点看不到；回报盘点结论时注明盘的是
  “磁盘上的已保存状态”。

## 6. 导出注意

- 导出前先确认已加载图层就是要导出的图层（图层来源 source 字段：
  opened-workspace / app-preloaded / none），导错会话是无头形态最常见的坑。
- 导出范围、分辨率、格式参数在当前版本均未经实机校准：先小样试导，
  拿落盘文件核对尺寸与内容，再批量执行；参数签名以校准结论为准回写文档。
- 导出目标目录须预先存在且可写；写失败与“函数调通但没文件”分开回报。

## 7. 迁移验收（用 verify_project.py）

```
<python> scripts/verify_project.py --workspace <工程.gmw>
<python> scripts/verify_project.py --workspace <工程.gmw> --copy-to <新目录>
```

交付/迁移前清单：

1. 工程 + 同主名伴生 + 被引用数据整组复制到新路径，对副本重跑盘点。
2. 被引用文件存在性逐项为真；.shp 伴生集必需件齐全。
3. 图层数与图层名（模块路线）与原工程一致；只有文本部分解析时，
   结论必须标注“部分解析、可能不完整”。
4. `issues` 列表逐条有处置或书面说明，不许只贴“为空”。
5. 原件 mtime 全程未变。
6. 导出 PNG 非空、内容合理（涉及导出交付时）。

## 8. 失败如实回报

- 模块不可用、候选函数全灭、上下文不成立，都是结构化结论，不是脚本坏了：
  回报原始 JSON（含 attempts / error_code），结论里写清“未实机验证”口径。
- 不许把 partial-parse 的推测图层名当成真实图层名汇报；不许把
  “函数没报错”说成“操作成功”（见第 4 节）。
- 许可/版本报错即停，回报原文，不换环境反复试探。
